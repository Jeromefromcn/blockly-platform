## 設計決策

### Like 系統設計
- **決策：** 採用 `clientId`（UUID 儲存於瀏覽器 `localStorage`）來識別每個瀏覽器的按讚行為，不依賴 user auth。
- **決策：** 改為單向按讚（不可取消），原因是取消按讚需要身份驗證機制，目前系統尚未實作 user auth。
- 相關資料庫新增 `client_id` 欄位與 unique constraint，防止重複按讚。

### 自動評分系統設計
- **決策：** 採用後端 JS 執行方式，使用 Mozilla Rhino engine，而非前端 browser sandbox 執行——後端執行更為可靠且一致。
- 兩種評分模式：
  - `OUTPUT_MATCH`：比對程式執行輸出值，Tutor 定義 test cases 為 JSON 格式：`[{"input": "expression", "expected": "value"}]`
  - `TRACE_MATCH`：比對程式執行 trace array
- 自動評分在以下時機觸發：單筆 JSON import、ZIP batch import。

### 系統 Workflow 確認
完整流程如下：
1. Tutor 在新平台建立題目
2. 學生在新平台做題
3. 學生匯出 JSON（含 `generatedCode`）
4. 上傳至學校 LMS（如 Moodle）
5. Tutor 從 LMS 匯出
6. Tutor 匯入至新平台 → 自動評分
7. Tutor 人工複查
8. 匯出 CSV 成績單

## Bug 修復

### Blockly `text_print` Block 相容性修復
- **問題：** Blockly 的 `text_print` block 預設產生 `window.alert()`，但 Rhino engine 沒有 `window` 物件，導致後端自動評分執行失敗。
- **修復 1（前端）：** 在 `BlocklyWorkspace.jsx` 中 override `text_print` 的 code generator，改為使用 `print()`。
- **修復 2（後端）：** `AutoGradingService.java` 同時 mock `print()` 與 `window.alert()`，確保向後相容。
- 相關檔案：`BlocklyWorkspace.jsx`、`AutoGradingService.java`

## 技術討論結論

### 自動評分架構
- 後端執行（Rhino）優於前端執行（browser sandbox），原因：結果一致、可稽核、不受學生瀏覽器環境影響。
- `OUTPUT_MATCH` 模式：執行 test case expression，比對回傳值。
- `TRACE_MATCH` 模式：執行完整程式，比對執行過程中的 trace log array。
